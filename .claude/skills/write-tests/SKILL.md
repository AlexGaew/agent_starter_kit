# write-tests

Процедура написания юнит-тестов в рамках TDD (см. правило `.claude/rules/tdd.md`).

## Шаги

1. Определи поведение одной фразой: что должно происходить при каком входе. Если требование неоднозначно, сверься с `docs/spec.md` и спроси пользователя.
2. Найди существующие тесты рядом с изменяемым кодом и повтори их стиль и структуру.
3. Напиши один тест на одно поведение в схеме given / when / then. Имя теста описывает поведение, а не метод.
4. Запусти тест (команда в `AGENTS.md`, раздел «Команды») и убедись, что он падает по ожидаемой причине, а не из-за ошибки компиляции или настройки.
5. Остальные тесты пиши по одному, повторяя шаги 3–4 для каждого.

## Что покрывать

- Основной сценарий и граничные случаи: пустой ввод, очень длинный ввод, повтор одного и того же.
- Отказ в доступе, если он есть в проекте: ничего не отвечать и ничего не сохранять.
- Сбой внешних сервисов: недоступны, вернули мусор. Данные пользователя при этом не должны теряться.

## Чего не делать

- Не ходить в сеть и в реальные внешние сервисы: клиенты подменяются заглушками.
- Не подключать реальную БД в юнит-тестах; для запросов к БД нужен отдельный интеграционный тест.
- Не проверять детали реализации (порядок вызовов, приватные методы), только наблюдаемое поведение.
